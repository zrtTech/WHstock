# Макет v12 — 64 адреса и безопасная RFID-инвентаризация

**Файл:** [UI_PROTOTYPE_V12.html](UI_PROTOTYPE_V12.html) — скачать Raw и открыть в Edge/Chrome. Это автономный интерактивный HTML-макет без установки и без внешних библиотек.  
**Проверка:** `node UI_PROTOTYPE_V12.test.cjs` — 22 регрессионных теста, Node.js, без npm.  
**Предыдущая версия:** `UI_PROTOTYPE_V11.html` сохранена без изменений.

## Адреса хранения

- **8 стеллажей**, у каждого **2 стороны: L — левая, R — правая**.
- На каждой стороне **4 ряда, сверху вниз: 1, 2, 3, 4**.
- Итого **64 фиксированных адреса**: `1L1`, `1L2`, …, `1R1`, …, `8R4`. Формат строго `[1-8][LR][1-4]`, без дефисов и пробелов.
- Экран «Сменить ряд»: сначала стеллаж 1–8, затем сторона L/R, затем один из четырёх рядов в физическом порядке сверху вниз. Можно также сканировать QR `RACK:1L1`.
- «Склад» показывает сводку по всем 64 адресам и переключение между 8 стеллажами. Рабочий адрес применяется к созданию и проверке.
- **QR места** печатается по желанию и клеится **на стационарный ряд стеллажа**, а не на образец. При перемещении образца QR не требуется менять. QR не является уникальным ID образца и не подтверждает его физическое положение.

## Почему RFID не подтверждает местонахождение

При инвентаризации выбранного ряда C5 может обнаружить EPC из соседнего ряда. Поэтому в v12 существуют **два независимых слоя**:

1. **Радионаблюдение** — EPC прочитан во время сессии проверки адреса. Записываются уникальные EPC, число чтений, последнее RSSI (если передано), время и источник. **Ни число чтений, ни RSSI не доказывают адрес**. Повторы не увеличивают число уникальных образцов.
2. **Физическая сверка** — отдельное решение оператора по конкретным экземплярам: «Физически здесь», «Соседний ряд / ложное чтение», «Вернул на учётный адрес», «Найден здесь» либо подтверждённое перемещение. Решение сохраняется в журнале.

### Сценарии расхождений

| Ситуация | Что делает оператор | Изменение учётного адреса |
| --- | --- | --- |
| C5 считал метку из соседнего ряда | «Соседний ряд / ложное чтение» | **Нет** |
| Образец действительно оказался в выбранном ряду | «Подтвердить: физически здесь», затем «Закрепить здесь» | **Да, только после двух отдельных действий** |
| Образец физически вернули на его прежнее место | «Вернул на учётный адрес» | **Нет** |
| Учётный образец не был считан, но найден руками | «Подтвердить: найден здесь» | **Нет** |
| Образец обнаружен в другом ряду | «Переместить в другой ряд» → выбрать адрес → ввести/сканировать адрес → отметить личную физическую проверку всех экземпляров → подтвердить | **Да, после явного подтверждения** |
| Образец не был считан | Оставить на проверку | **Нет; не удаляется** |

- Список «Не считаны» составляется из экземпляров, **имеющих EPC на момент начала проверки**. Экземпляры без EPC не объявляются пропавшими из-за отсутствия RFID.
- «Чужие сигналы» — кандидаты для физической сверки, а не автоматически доказанные перемещения.
- Завершение проверки само по себе не перемещает и не исключает образцы.
- Для массовой коррекции выбранные экземпляры должны быть однозначно определены, а физическая проверка должна относиться **к каждому**.

## Приём данных Chainway C5 — контракт демомакета

**Запись и привязка EPC к конкретному образцу — только на Chainway C5.** Windows-макет не записывает метки и не имеет ручного поля привязки. Приём подтверждённой привязки из v11 сохранён: `receiveC5Binding(event)` проверяет `eventId`, `sampleId`, `barcode`, `epc`, `readBackEpc`, `confirmed`, `expectedVersion`, уникальность EPC и идемпотентность.

Для **пакета радионаблюдений** v12 добавлена демонстрационная функция `receiveC5Inventory(event)`:

```json
{
  "eventId": "c5-read-0001",
  "sessionId": "id-активной-проверки",
  "rack": "1L1",
  "reads": [
    { "epc": "E20000000000000000000001", "readCount": 5, "rssi": -52 },
    { "epc": "E20000000000000000000002", "readCount": 2, "rssi": -67 }
  ]
}
```

`eventId` защищает от повторного применения одного пакета. Пакет принимается только для активной проверки указанного ряда, валидируется по формату EPC, `readCount` и `rssi`. Сопоставленные EPC добавляются **только как наблюдения**, в том числе если их учётное место отличается от сканируемого. Неизвестные EPC фиксируются отдельно. В реальной интеграции потребуются авторизация, подпись/проверка источника, транспорт, синхронизация и обработка офлайна.

## Другие сохранённые сценарии

- Поиск товара по артикулу, названию и товарному штрихкоду. Несколько физических образцов могут иметь **общий товарный ШК**; уникальный EPC связывается с отдельным экземпляром на C5.
- Массовое создание, включая демопартию **100 образцов**. Печать индивидуальных этикеток не обязательна.
- Демо-остатки «1С» и выбираемый порог **0,5 м или 1 м** для списка кандидатов на **ручное** исключение. Автоматического удаления по остатку нет.
- Исключение из активного учёта требует явного выбора и подтверждения, сохраняет запись и событие (демо-аудит).
- Журнал событий, просмотр состояния EPC, экспорт демоданных в JSON.
- Состояние хранится в отдельном ключе браузера `fabric-prototype-v12`. Данные v11 **не переносятся автоматически**, поскольку старые коды полок нельзя надёжно сопоставить с новой схемой адресов. Оба макета независимы.

## Как проверить вручную

1. Открыть HTML → «Склад» → «Работа на полке» → «Сменить ряд» → выбрать, например, `1L1`.
2. «Проверить ряд» → «Начать проверку» → «Демо: чтения своего и соседнего ряда». Убедиться, что у меток из соседних рядов **учётные адреса не изменились**.
3. «Завершить проверку» → «Разобрать чужие сигналы». Проверить «Соседний ряд / ложное чтение»; затем на другом экземпляре «Подтвердить: физически здесь» → «Закрепить здесь».
4. Для перемещения в иной ряд проверить, что без галочки личной физической проверки и без совпадающего введённого адреса действие не выполняется.
5. Открыть «Журнал» и проверить, что решения записаны. В «Аналитике» проверить порог остатков.
6. «Печать QR места» → выбрать адрес → проверить предпросмотр `RACK:1L1` и стандартный диалог печати.

## Ограничения и требования к промышленной версии

**v12 — браузерный UX-макет, не готовая складская система.** Данные вымышлены; нет настоящих 1С:УНФ, Chainway C5, RFID SDK, API, сервера, SQL, аутентификации, серверных транзакций и неизменяемого аудита. `localStorage` и `window.confirm` — только демонстрационные механизмы; им нельзя доверять как промышленному контролю.

Перед внедрением потребуются реальные испытания перекрёстных считываний на складе, настройка мощности/дистанции/режима антенны C5, проверка каждого перемещения, серверные атомарные операции и журнал, обработка параллельных действий и офлайн-пакетов, авторизованная интеграция с C5, **чтение** остатков из 1С:УНФ и испытания QR/принтера. RSSI не следует превращать в автоматическое доказательство номера ряда.
