# UX-аудит макета v5: каждый экран, пробелы, сокращения и автоматизация

Дата: 2026-10-29. Основа: `UI_PROTOTYPE_V5.html` в этой ветке. Это аудит **демонстрационного HTML**, а не утверждение о готовой Windows-программе. Демоданные: 140 товаров, 80 образцов, 4 полки. Предполагаемая целевая система: порядка 10 000 товаров, Windows desktop, 1С УНФ только чтение, Chainway C5 UHF RFID/2D, USB-HID 2D, собственная БД и независимый фоновый API. Проверить окружение до реализации.

## Краткий вердикт

Макет содержит 14 типов экранов и много промежуточных шагов. Оператору нужны 3 операции над экземпляром (**создать, переместить, убрать из активного учёта**) и отдельная **проверка-наблюдение**. Исправление расхождений — контекстная работа с результатами проверки, а не четвёртая складская операция. Просмотр памятки — не выполненное физическое перемещение.

Рекомендуемая навигация: **Работа на полке**, **Найти образец**, **Склад / проверки**, вторично **Отчёты** и **Журнал**. Полку выбирать сканированием кода или кликом без лишнего подтверждения, но фиксировать контекст в момент операции.

## Поэкранный аудит

### 01. «Обзор всего склада» — `overview()`
- Сейчас: 8 KPI, таблица полок, ещё три больших карточки «Что требует внимания». Дублирование ссылок на одни и те же списки.
- Проблема: показатели «Чужие»/«Не найдены» пересчитываются по изменяемым полям образца, хотя подписи говорят о завершённых проверках; «Полок проверено» не показывает давность; «Нулевой остаток» конкурирует с физическими проблемами.
- Решение: 4 основных показателя — активные экземпляры, открытые расхождения, полки без актуальной проверки, последняя проверка/синхронизация. Остальные — фильтры/отчёты. У каждого счётчика прямой переход в рабочий список. Разделить **исторический результат проверки** и **открытые расхождения сейчас**.

### 02. «Все полки склада» — `racksPage()`
- Сейчас: отдельная карточная страница, повторяет таблицу из обзора.
- Проблема: вечный ярлык «Проверена», не видно давности, незавершённых сеансов, несинхронизированных событий.
- Решение: единый список полок с поиском, количеством по учёту, датой последней завершённой проверки, открытыми проблемами и состоянием сеанса. Открытие полки одним кликом. Отдельную страницу оставить лишь при большом числе полок; иначе встроить в обзор.

### 03. «Аналитика» (6 вкладок) — `analytics()`
- Сейчас: все товары, без образца, не на месте, не найдены, нулевой остаток, все образцы; поиск в выбранной вкладке.
- Проблема: нет единого поиска по **уникальному коду экземпляра / EPC / товарному ШК / артикулу**; в проблемных списках только «Открыть полку», не «Решить»; таблицы рендерятся целиком (нельзя так для 10 000); выделенные товары могут остаться вне текущего фильтра и всё равно попасть в очередь.
- Решение: разделить **Найти образец** (операционный поиск с прямым действием) и **Отчёты** (фильтры). Серверный поиск, пагинация/виртуализация, явный охват выделения. «Без образца» не означает «создать обязательно». Остаток 1С — справка с временем обновления, не команда на удаление.

### 04. «Работа с полкой» — `home()`
- Сейчас: добавить, проверить, исправить места, убрать; сводка последней проверки.
- Проблема: отсутствует прямое **перемещение известного образца** без запуска проверки; «Исправить места» выглядит как самостоятельная операция.
- Решение: 4 задачи: **Добавить**, **Переместить**, **Проверить**, **Убрать**. Под результатами проверки — контекстный блок «Разобрать N расхождений», если они есть. Для одного образца достаточно сканирования уникального кода и назначения полки.

### 05. «Выбрать рабочую полку» — `shelfPage()`
- Сейчас: выпадающий список, ввод RACK:..., кнопка «Подтвердить полку».
- Проблема: лишнее подтверждение после корректного сканирования; при смене полки может переназначиться вся очередь создания; глобальные переходы могут сменить контекст посреди сценария.
- Решение: валидный ШК полки выбирает её автоматически с заметным заголовком; для выбора мышью — клик по полке. При непустой очереди смена полки — явное предупреждение «Сохранить текущую / переназначить / отменить». Во время подтверждения операции полка фиксирована и не меняется.

### 06. «Добавить образцы» — `create()` (сканирование + проверка)
- Сейчас: скан товарного ШК, счётчик повторов, кнопки «Добавить скан», «Загрузить пример 100 товаров», «Очистить», «Проверить и создать», затем «Создать».
- Проблема: «Добавить скан» избыточна при Enter; демокнопка недопустима в боевом UI; неизвестный код можно только убрать; одинаковый товар, отсканированный по артикулу и ШК, попадает в разные строки; нет реальной привязки уникального ШК экземпляра / EPC и печати/учёта этикетки.
- Решение: сканирование без кликов; нормализовать по ID товара 1С; один компактный список с количеством и явным предупреждением о повторе; «Создать N» с одной итоговой проверкой. **Не объявлять экземпляр полностью введённым в оборот без способа однозначно идентифицировать физическую бирку**: печать уникальных этикеток или привязка заранее маркированных кодов, EPC — отдельный проверяемый сценарий. Решение о печати/предмаркировке — бизнес-вопрос, не догадка Codex.

### 07. «Проверить полку» — `inspect()` (начало + сканирование)
- Сейчас: отдельный старт, поток USB-сканов, очередь неразобранных, завершение вручную, демозагрузка.
- Плюс: expected snapshot на старте; повторный уникальный код не увеличивает найденных; отсутствие не считается удалением; завершение заблокировано при неоднозначных сканах.
- Проблема: обработчик `oninput` распознаёт полный код без Enter, что рискованно при HID-потоке; товарный ШК может быть ошибочно принят за подтверждение конкретного экземпляра; нет реального C5, EPC, офлайна, синхронизации и источника событий. Нет живого разделения «свои / чужие / неизвестные», недостаточно ясна полнота обхода полки.
- Решение: автоматическая обработка **завершённого** скана (HID Enter/событие C5), уникальный экземпляр по sampleCode/EPC, товарный ШК только при гарантированной однозначности и явной индикации. Сканирование без подтверждений, звуковая/визуальная обратная связь. Завершение **только вручную** (оператор решает, что обход закончен), с итогом «свои / чужие / не найдены / неразобранные». Неразобранные не терять; офлайн C5 показывает очередь и статус отправки.

### 08. «Проверка завершена» — `afterInspect()`
- Сейчас: отдельная страница итогов с тремя кнопками.
- Проблема: лишний экран перед действиями; «Главный экран» и «Исправить» заставляют повторять навигацию.
- Решение: это **верхняя часть единого экрана результата проверки**, под ней сразу две вкладки «Чужие» и «Не найдены» с действиями. Никакого отдельного «перейти к исправлению». Результат проверки неизменяем, а состояние разбора проблем обновляется отдельно.

### 09. «Исправить места» — `fix()`
- Сейчас: выбор вкладки проблемы → чекбоксы → «Выбрать все» → «Выбрать действие для N».
- Проблема: слишком много действий для типового решения «50 чужих обнаружены на этой полке — оставить здесь». Нет поиска/фильтра и построчных быстрых действий.
- Решение: сразу показывать строки с **«Оставить здесь»** и **«Вернуть на учётную полку»**; при массовом выборе — одна контекстная панель действий с числом выбранных и учётными полками. Для «Не найдены» не требовать специального «пометить для поиска»: это уже открытая проблема автоматически.

### 10. «Выбрать действие» — `fixAction()`
- Сейчас: 3 варианта для чужих; 4 для не найденных, затем «Проверить действие».
- Проблема: `search` создаёт отдельное ручное состояние без необходимости; `physical` показывает памятку как будто это операция; «Переместить на другую полку» допускает ту же полку; подтверждение «нашёл все N» — ручное заявление, не доказательство сканирования.
- Решение: для чужих — **«Закрепить здесь»** (изменить учёт), **«Вернуть физически»** (показать учётные адреса, не менять учёт), **«Переместить на другую»** (с фактическим подтверждением). Для не найденных — **«Нашёл здесь»** (новое наблюдение), **«Нашёл в другом месте»** (наблюдение + явное изменение учёта), **«Убрать из активного учёта»** (отдельная опасная операция). Не найденные уже находятся в очереди разбора, «В поиске» можно считать автоматическим статусом открытой проблемы. Проверку физического обнаружения сделать доступной через скан уникального ID, но не требовать повторного скана для ранее наблюдённых «чужих».

### 11. «Проверьте перед подтверждением» — `preview()`
- Сейчас: отдельная третья ступень практически для всех действий, включая неопасные.
- Проблема: лишние переходы; при возврате из удаления навигация зависит от `S.issue`, а не от реального источника действия.
- Решение: **диалог подтверждения только для удаления и массовых изменений мест**; одиночное явное перемещение — одна команда с кратким результатом. В диалоге: N, откуда → куда, что изменится, что останется без изменений. Источник возврата хранить явно (`returnTo`), не выводить из последнего фильтра.

### 12. «Убрать ненужные образцы» — `removePage()`
- Сейчас: фильтр по умолчанию — товары с нулевым остатком, затем «Выбрать все» и красная кнопка.
- Проблема: опасная связь с 1С; нулевой остаток не означает, что физический образец больше не нужен. «Выбрать все» на таком фильтре — риск массовой ошибки.
- Решение: открывать **по скану уникального образца / поиску / текущей полке**. Нулевой остаток показывать только как вспомогательный фильтр с отметкой давности данных, никогда не как предвыбранный список для удаления. При удалении N образцов явно показывать все идентификаторы/количество, сохранять tombstone и неизменяемый аудит, не предлагать архив/восстановление.

### 13. «Результат операции» — `result()`
- Сейчас: отдельный экран с числом обработанных и кнопками «Главный экран», «История».
- Проблема: прерывает поток сканирования; полка результата может не соответствовать реальному контексту; при создании не решает задачу физической маркировки.
- Решение: компактный результат на том же экране, фокус на следующий скан. Для массовой операции — итог с ошибками/конфликтами; для создания — список уникальных кодов и печать/привязка меток; для удаления — подтверждение количества и ссылка на аудит.

### 14. «История действий» — `historyPage()`
- Сейчас: краткие записи только до F5, без подробностей.
- Проблема: не видно кто/когда/что именно изменил, старое и новое место, какой образец, откуда пришло событие, requestId, версии. Нельзя разбирать спорные операции.
- Решение: неизменяемый журнал с поиском по sampleCode/EPC/товару/полке, фильтрами даты/операции/источника; детали до/после, актор, время, requestId, version. История конкретного образца доступна прямо из карточки.

## Подтверждённые дефекты v5 (воспроизведены исполнением JavaScript макета)

**P0-01. История проверки меняется задним числом.** Старт: у B-01-02 50 «чужих». Провести проверку A-02-03, отметить S-000001 и завершить. Итоговый счётчик «чужих» для B становится **25**, хотя сохранённый `lastByRack["B-01-02"].seen` не изменялся. Причина: `rackWrong()` зависит от изменяемого `x.inspected` и `x.seen`, которые перезаписываются новой проверкой. **Исправление:** неизменяемые строки observation/expected внутри каждого сеанса; отдельно открытые проблемы и события разрешения.

**P0-02. Глобальная отметка «найден» скрывает пропуски будущей проверки.** Отметить 8 «не найденных» на B как найденные. Запустить новую проверку B и завершить без единого скана. В новом снимке ожидаются **20**, фактически не найдены все **20**, но интерфейс показывает **12** из-за глобального `S.resolvedMissing`. **Исправление:** разрешение привязано к конкретному issue/inspection, новая проверка создаёт новые проблемы.

**P0-03. Неправильный возврат из удаления.** После выбора вкладки «Не найдены» открыть самостоятельное «Убрать образцы» → предпросмотр → «Назад без изменений»: возврат попадает в `fixAction`, потому что `preview-back` проверяет `S.issue`. Обратный случай: верхний «Назад» из удаления, инициированного на вкладке «Не найдены», ведёт на экран удаления вместо выбора действия. **Исправление:** явный `origin`/маршрут.

**P1-04. «На другую полку» допускает ту же полку.** В сценарии чужих выбрать `other`, указать текущую B-01-02, предпросмотр разрешён. Требуется валидация целевого места и смыслового действия.

**P1-05. Протокол поиска и обнаружения не сохраняется.** `searchNeeded`/`resolvedMissing` — глобальные массивы в памяти, не события, не привязаны к версии/сеансу. В демо это допустимо только как временная визуализация.

**P1-06. Учётная модель демонстрации не доказывает физическую идентичность.** `create-confirm` создаёт уникальный `S-...` в памяти без выдачи/привязки физической этикетки или EPC. В боевой системе требуется жизненный цикл маркировки.

## Что отсутствует целиком (не путать с дефектами HTML)

1. **Глобальный быстрый поиск / карточка экземпляра.** По уникальному коду образца, EPC, товарному ШК/артикулу (с выбором экземпляра при неоднозначности), текущей полке, последнему наблюдению, статусу, истории. Из карточки — «Переместить» и «Убрать».
2. **Прямое перемещение.** Скан экземпляра → скан полки назначения (или заранее выбранная) → явная фиксация без обязательной проверки полки.
3. **Маркировка.** Выдача уникального ШК экземпляра, печать/преднапечатанные бирки, привязка и перевязка EPC с контролем уникальности и интервальной историей; состояние «ожидает маркировки» при необходимости. Не путать товарный ШК с sampleCode.
4. **Экран C5.** Выбор полки, RFID/2D наблюдения, дедупликация, неизвестные EPC, локальная офлайн-очередь, счётчик неотправленных, синхронизация с фоновым API, защита от повторной доставки. Конкретные возможности C5/SDK проверять на устройстве.
5. **Состояние интеграций.** Последнее успешное чтение каталога 1С, свежесть остатков, ошибки чтения, статус фоновой службы, доступность C5, резервные копии. Никаких записей в 1С.
6. **Настоящая неизменяемая история и независимые снимки проверок.** Expected snapshot на старте, observations как события, проблемы и их разрешения отдельно; пересчёт открытых проблем не переписывает итог завершённой проверки.
7. **Права, транзакции, конфликты, идемпотентность, восстановление.** `requestId+payloadHash`, optimistic versions, уникальный активный EPC, атомарные пакеты, аудит, миграции, резервные копии и тест восстановления. Макет только имитирует конфликт/сеть.
8. **Работа с большим объёмом.** 10 000 товаров: индексы, поиск на сервере, страницы/виртуализация, сохранение выбора с ясным охватом фильтров.
9. **Восстановление рабочего процесса.** Незавершённые партии, активная проверка, C5 офлайн-пакеты должны переживать перезапуск GUI; фоновой сервис независим от окна.
10. **Операционные состояния.** Полка не проверялась / проверка в процессе / проверена с датой / есть неотправленные события / есть открытые расхождения. «Нет данных» не равно 0.

## Сокращение кнопок и шагов

| Сейчас | Рекомендуется | Экономия/эффект |
|---|---|---|
| Выбор полки → «Подтвердить полку» | Скан кода полки сразу выбирает полку | −1 клик, явный контекст |
| «Добавить скан» после HID Enter | Автоматически принимать завершённый скан | −1 клик на экземпляр |
| «Проверить и создать» → отдельный обзор → «Создать» → отдельный результат | Одна кнопка «Создать N» → один диалог проверки → продолжить сканирование/маркировку | Меньше переходов |
| «Проверка завершена» → «Исправить» → выбор вкладки | Сразу итог проверки и открытые проблемы на одной странице | −1–2 экрана |
| «Выбрать все» → «Выбрать действие» → выбор действия → «Проверить» → «Подтвердить» | Чекбоксы + постоянная панель «Закрепить здесь / Другое действие»; диалог только для массового изменения | −2–3 шага |
| «Не найдены» → «Оставить в списке поиска» | Все не найденные автоматически открыты для поиска | Убрать отдельную кнопку и псевдооперацию |
| «Разнести физически» → предпросмотр → «Показать памятку» → результат | «Куда отнести» раскрывает список адресов без фиктивной операции | −2 экрана |
| «Удаление» по умолчанию фильтр «Остаток 0» | Поиск/скан уникального образца, затем явное исключение | Меньше риска |
| Отдельный «Результат» после каждого действия | Inline-уведомление и возврат фокуса на сканер | Непрерывный поток |
| «Открыть полку» из проблемной аналитики → снова искать проблему | «Разобрать проблему» открывает точную полку и вкладку/строку | −2–3 клика |

**Не автоматизировать:** завершение проверки (только оператор знает, что полку полностью обошёл), изменение учётной полки по одному лишь факту RFID-наблюдения, исключение из активного учёта, выбор конкретного экземпляра при неоднозначном товарном ШК, подмену результата неопределённого сетевого запроса новым requestId.

## Рекомендуемые компактные сценарии v6

1. **Работа на полке:** скан RACK → видна полка → четыре действия: добавить / переместить / проверить / убрать. Можно сразу сканировать экземпляр в глобальном поиске.
2. **Создание:** выбранная полка → поток товарных ШК → компактная очередь с qty → «Создать N» → получить уникальные идентификаторы и физически привязать этикетки/EPC. Не создавать 1С-документы.
3. **Перемещение:** скан уникального образца → выбрать/сканировать полку назначения → «Переместить»; массово — выделить несколько и подтвердить один раз.
4. **Проверка:** выбранная полка → «Начать» (заморозить expected) → поток C5/USB → «Завершить» вручную → сразу видны «Чужие / Не найдены» и быстрые решения. Скан не перемещает.
5. **Разбор чужих:** «Закрепить здесь» одним явным действием; «Куда вернуть» — только адресная памятка; другая полка — прямое перемещение с подтверждением факта.
6. **Разбор не найденных:** проблема открывается автоматически. При физическом обнаружении — «Нашёл здесь» (новое наблюдение) или «Нашёл на другой» (наблюдение + перемещение). При осознанном исключении — опасное действие с подтверждением. Исторический отчёт остаётся неизменным.
7. **Удаление:** поиск/скан уникального экземпляра → «Убрать из активного учёта» → явное подтверждение, immutable tombstone; никаких архивов/восстановлений.

## Приоритет Codex и критерии готовности

### P0 — исправить модель до нового дизайна
- Неизменяемые expected/observations каждого inspection; отдельно issue и issue_resolution; новый inspection не наследует разрешения прошлого.
- Корректная навигация с явным origin/returnTo; заблокировать изменение контекста полки в подтверждении.
- Прямое перемещение, уникальная физическая идентичность образца, никакого автоматического удаления из-за нулевого остатка.
- Сценарии восстановления и идемпотентности API до реального подключения C5.

### P1 — сократить действия
- Убрать отдельный afterInspect, лишний preview для безопасных операций, отдельный result для каждого скана, «Добавить скан» при Enter, ручную отметку «в поиске», фиктивный commit памятки.
- Сделать контекстные массовые действия и быстрые построчные операции.
- Глобальный поиск и прямая карточка экземпляра.
- Физическая маркировка и EPC-binding как завершённый сценарий.

### P2 — эксплуатация и аналитика
- Даты/источники/свежесть проверки и каталога, статус фоновой службы/C5, поиск/фильтры/пагинация, журнал по экземпляру, диагностика и восстановление.

### Приёмочные сценарии, обязательные для реализации
1. B: завершённая проверка с 50 чужими и 8 не найденными. Новая проверка A не меняет **исторические** числа B. Текущие открытые проблемы могут меняться только через явно определённые события/правила.
2. Разрешить 8 пропусков B, затем начать новый пустой обход B с expected=20: новая проверка показывает **20 пропусков**, а не 12.
3. Удаление из «Не найдены» и из отдельного экрана всегда возвращается в правильный источник.
4. Два экземпляра одного товара имеют разные sampleCode и EPC (если привязаны). Скан товарного ШК при неоднозначности не выбирает экземпляр сам.
5. RFID повтор, офлайн-переотправка, конфликт версии, обрыв после commit: без двойной записи и без выдуманного успеха.
6. Скан на чужой полке не перемещает; «Закрепить здесь» меняет место один раз и пишет audit.
7. Нулевой остаток 1С сам ничего не удаляет; 1С остаётся строго read-only.
8. Незавершённая партия, проверка и очередь C5 переживают перезапуск GUI/сервиса согласно утверждённой стратегии восстановления.
9. Для 10 000 товаров таблицы не рендерят все строки сразу; поиск и выбор корректны с фильтрами.
10. Тесты на реальном C5/USB/1С обязательны до объявления интеграций готовыми; нельзя подменять их демоданными.
