# Аудит UI/UX и системных улучшений

## Контекст
Проверен текущий одностраничный складской терминал (`index.html`) с kiosk-потоком, режимом персонала, локальным хранилищем, интеграциями печати и 1С.

## Ключевые проблемы и предложения

## 1) UX и интерфейс

### 1.1. Нет явной системы состояния и обратной связи
- Сейчас многие действия молча завершаются при невалидном вводе (`return` без объяснения), например при сохранении строки без артикула или метража.
- **Улучшение:** добавить inline-валидацию рядом с полями + явный текст ошибок в toast.
- **Эффект:** меньше «тихих» отказов, выше скорость работы оператора.

### 1.2. Слишком плотные экраны для терминалов
- В рабочих формах много полей подряд без визуальных подзаголовков/этапов.
- **Улучшение:** разбить формы на блоки: «Товар», «Локация», «Количество», «Действия».
- **Эффект:** проще обучение новых сотрудников и меньше промахов на сенсорных экранах.

### 1.3. Управление модалками ограничено
- Нет явной поддержки закрытия модалок по `Esc` и клику по оверлею, не реализован фокус-трап.
- **Улучшение:** добавить доступное модальное поведение (focus trap, aria-role, Esc/overlay close).
- **Эффект:** лучше управляемость и доступность (a11y).

### 1.4. Используются эмодзи как единственные иконки действий
- Эмодзи различаются между платформами и иногда читаются неочевидно.
- **Улучшение:** оставить эмодзи как вспомогательные, но добавить текстовые подписи для критичных действий (`Удалить`, `Редактировать`, `Печать`).
- **Эффект:** меньше когнитивной нагрузки и ошибок.

## 2) Доступность (a11y)

### 2.1. Недостаточная семантика
- Почти нет ARIA-атрибутов для модалок и статусов, отсутствуют live-region для toast.
- **Улучшение:**
  - `role="dialog"`, `aria-modal="true"` для модалок.
  - `aria-live="polite"` для уведомлений.
  - `aria-label` для icon-only кнопок.

### 2.2. Контраст и фокус
- Есть стили `:focus` только для `input`, а для `button/select` явно не оформлены.
- **Улучшение:** единый заметный focus-ring для всех интерактивных элементов.

## 3) Надежность и безопасность

### 3.1. Пароль менеджера хранится в localStorage
- `sets.mgr` и флаг `isMgr` сохраняются локально.
- **Риск:** легкий обход авторизации при доступе к устройству.
- **Улучшение:** минимально — хэш пароля + тайм-аут сессии; лучше — проверка на сервере и short-lived токен.

### 3.2. Уязвимость XSS через `innerHTML`
- Много мест, где пользовательские данные вставляются через шаблонные строки в `innerHTML`.
- **Улучшение:** для пользовательских значений использовать `textContent` и явную санацию.
- **Эффект:** защита от инъекций и поломки верстки.

### 3.3. Нет версионирования структуры данных
- `safeLoad` загружает объекты как есть, миграций схемы нет.
- **Улучшение:** добавить `schemaVersion` + миграции при загрузке.
- **Эффект:** безопасные обновления без потери данных.

## 4) Архитектура и поддерживаемость

### 4.1. Монолит в одном файле
- HTML/CSS/JS находятся в одном `index.html`, что затрудняет тестирование и расширение.
- **Улучшение:**
  - `index.html`
  - `styles/main.css`
  - `scripts/app.js`, `scripts/state.js`, `scripts/ui.js`, `scripts/integrations.js`
- **Эффект:** более быстрые изменения и меньше регрессий.

### 4.2. Глобальное состояние и side effects
- Множество глобальных переменных (`db`, `sets`, `curTab`, `curDocId`) и функций, тесно связанных с DOM.
- **Улучшение:** ввести слой state/store + чистые функции для бизнес-логики.

### 4.3. Дублирование форм и рендеринга
- Большие шаблонные строки для каждой вкладки, повторяются секции ввода/кнопок.
- **Улучшение:** компонентный рендер через функции-шаблоны и общий конструктор полей.

## 5) Производительность

### 5.1. Перерисовка всей области
- Часто полностью пересоздаются контейнеры (`innerHTML = ""` + полная генерация).
- **Улучшение:** точечные обновления (изменять только затронутый элемент), либо lightweight view layer.

### 5.2. Данные в localStorage
- Для крупных журналов localStorage ограничен и синхронный.
- **Улучшение:** перейти на IndexedDB для документов и логов.

## 6) Интеграции (1С, печать, экспорт)

### 6.1. Слабая диагностика сетевых ошибок
- Пользователь видит общие сообщения «Ошибка 1С»/«Сервер недоступен».
- **Улучшение:** выводить код ответа, endpoint, корреляционный ID и кнопку «Повторить».

### 6.2. Нет очереди синхронизации offline-first
- Если сеть недоступна, отправка в 1С просто падает.
- **Улучшение:** очередь исходящих документов + фоновая повторная отправка.

### 6.3. PrintNode/RawBT не имеют единых статусов
- Разные ветки логики без единого трекинга результата печати.
- **Улучшение:** единый `printService` с нормализованными статусами (`queued/sent/failed`).

## 7) Качество кода и тестирование

### 7.1. Нет автотестов
- **Улучшение:**
  - Unit: валидация, сериализация, миграции.
  - E2E: создание документа, редактирование, закрытие, экспорт/импорт.

### 7.2. Нет линтинга/форматирования
- **Улучшение:** добавить ESLint + Prettier + базовые pre-commit проверки.

## Приоритетный roadmap

### Этап 1 (быстрые улучшения, 1–2 дня)
1. Понятные ошибки валидации вместо «молчаливых return».
2. Единый focus style для `button/input/select`.
3. ARIA-атрибуты модалок и toast.
4. Безопасный вывод пользовательских данных (минимум в списках и карточках).

### Этап 2 (устойчивость, 3–5 дней)
1. Рефакторинг в отдельные JS/CSS модули.
2. Введение версионирования данных (`schemaVersion`) и миграций.
3. Очередь синхронизации для 1С (offline-first).

### Этап 3 (масштабирование, 1–2 недели)
1. Переход хранения на IndexedDB.
2. Покрытие ключевых сценариев E2E тестами.
3. Телеметрия бизнес-событий и ошибок (с обезличиванием).

## Быстрые метрики успеха
- Время на создание документа: **-20%**.
- Ошибки ручного ввода: **-30%**.
- Неуспешные синхронизации с 1С без повтора: **-50%**.
- Повторные обращения по UX-вопросам: **-25%**.
